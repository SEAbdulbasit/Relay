# Relay onboarding and identity — fresh design audit, 20 November 2026

This is an independent source audit of the current working tree. It does not claim independent runtime, VoiceOver, account, or minimum-window verification. The existing reliability changes are retained. No existing design skill or outside UI reference was used as a creative constraint.

## The central design opportunity

Relay's strongest product idea is an observable handoff: ask for an outcome, see what needs review, inspect what actually happened, keep the result. The current onboarding teaches a catalog of AI features. Its most distinctive future identity should instead make that handoff legible everywhere.

**Proposed direction: Relay Workbench.** An uncluttered place to turn an intention into checked work. Use one continuous line as the signature motif: intention → review → checked result. It is a navigation and evidence structure, not a decorative animated circuit. The point where the line stops is the next human decision. The final result is a legible receipt, not a shower of success badges.

## A coherent visual and interaction system

- **Geometry:** One large working surface with clear edges. Use 10–12-point control radii and 14–16-point surface radii. Avoid capsules for paragraphs, whole settings sections, and every navigation item. Keep pills for very short statuses and shortcuts.
- **Type:** System sans for clarity. Large sentence-case task headings, less uppercase architecture language. Monospaced numerals give expression/result receipts a recognizable instrument-like precision. A readable result should dominate its container; the explanation follows it.
- **Color:** Adaptive neutral paper/graphite surfaces. The primary action can remain black/white to preserve brand discipline; use blue for selected destinations and links. Green appears only after a real checked outcome, not simply after a selection.
- **Signature:** A thin vertical or horizontal route joins three factual labels. A hollow endpoint means planned, an amber decision point means review, a solid checked endpoint means verified outcome. Never animate an unreal completion merely for ambience.
- **Motion:** Focus movement, expanding a receipt, and real progress are enough. Successful local calculation may introduce the actual result with one brief opacity/position transition; reduced motion gets immediate layout. Persistent orbiting particles and an auto-playing simulated cursor should be secondary practice content.
- **Language:** “Choose a model,” “Connect an account,” “Give access when you need it,” “Sources stay optional,” “Try a first task.” Remove “primary intelligence engine,” “architectural,” and “telemetry” as primary first-launch navigation concepts. Keep technical details available where a user makes a technical decision.

## Implementable scope for this iteration

A focused implementation can materially change the experience without rewriting permission/provider logic:

1. Redesign `welcomeStepView` and `localCalculatorTrial` as one left-aligned first-action composition: product promise, actual editable expression, explicit run action, a strong checked result receipt, compact trust notes.
2. Put `OnboardingWelcomePreview` inside an optional disclosure with a clear fictional-practice label. Keep its existing functionality and task cancellation intact.
3. Replace the general stage heading treatment with stronger task-led hierarchy while keeping every persisted step ID and accessible navigation value.
4. Add a small factual “You can use Relay now / Optional next” handoff on the final stage, based only on `store.workspaceActionsReady`, actual connection/readiness, and source counts. Do not assign completion based on selected tabs.
5. Simplify the onboarding footer into one primary continuation row and a modest privacy link. Keep the exact existing no-telemetry explanation available, but do not make three trust capsules compete with Continue.

Broader provider IA, timing/schedule consolidation, and app-wide tokens should follow coordinated ownership; do not make unilateral changes to all shared controls while other agents redesign workspace and Knowledge.

## Pitfalls and boundaries

- Preserve `stepOrder = [0, 3, 1, 2, 4]`, provider/model persistence, and the exact `welcomeStep`/`privacyStep` declarations called out as source-test contracts.
- The calculator is a real local tool and must remain explicitly triggered, editable, cancel-safe, error-capable, and evidence-backed. Do not convert it into a fake precomputed “success” illustration.
- No new permission grant, source opt-in, download, background schedule, credential, login registration, or external request should happen simply because a screen appears.
- Source selection, permission availability, completed indexing, and generated knowledge are different statuses; preserve their distinction.
- Existing single-agent live checks and multi-agent fixture checks do not qualify every external application task. The redesigned route must not imply stronger guarantees than the execution engine provides.
- A strong design review still needs central runtime screenshots and actual interaction checks. This audit is grounded in current source and behavior contracts, not a screenshot claim.

## Implementation delivered in this pass

- `OnboardingView.swift`: left-aligned workbench stage hierarchy, numbered quiet navigation, optional collapsed fictional welcome tour, permission example, and source map. The primary welcome content is now the real local action. Final source stage describes the actual selected workspace provider and keeps indexing/preparation separate. The footer clearly labels a selected model route and offers one continuation action; privacy details remain available through two text links.
- `OnboardingWorkbenchViews.swift`: isolated editable calculator work surface and genuine idle/running/checked/error receipt presentation. The production coordinator still owns invocation, checked-outcome admission, and retry. No arithmetic is precomputed by the view.
- Onboarding-local stage and provider/permission surfaces use the shared adaptive neutral canvas and card material. Shared global color and typography tokens are owned by the root agent; optional fictional preview internals retain their separate practice presentation when deliberately expanded.
- All persisted step IDs, exact `welcomeStep`/`privacyStep` declarations, provider wiring, source choices, permissions, and callback ownership remain intact. No account, source, schedule, download, login registration, or background task is started by the design changes.

`xcrun swiftc -frontend -parse Sources/Relay/OnboardingView.swift Sources/Relay/OnboardingWorkbenchViews.swift` passed. Scoped `git diff --check` passed. Shared compilation, screenshots, real interaction, and accessible-role checks are coordinated by the parent; no separate build or app control was run by this audit agent.

Deferred design work remains: progressive three-path provider selection instead of six equal tabs; a real post-connection first request; full enlarged-text/keyboard/VoiceOver qualification; simplifying the deeply nested schedule and bridge sheets; and applying the same adaptive workbench materials to optional fictional practice interiors. Those items are not claimed fixed by the current visual pass.
