## Conversation delivery and recovery

Relay now stores conversation events in an actual local system-SQLite journal. A started+user transaction must be acknowledged before the user message is delivered or a tool can dispatch. Home retains the originating draft until that acknowledgment; a duplicate pending Return/click reuses its delivery ticket, while edited steering remains a distinct request. Sidekick submits its own text without temporarily assigning Home's draft. Its unchanged prompt clears synchronously with delivery, and its result binds the exact submitted message ID. Hiding the panel keeps the shared task running. Stop, session suspension, retirement and late acknowledgments preserve edited text and cannot stop a newer task through an old ticket.

Each direct, ordinary, multi-agent and specialized native dispatch records an acknowledged intent before entering its actual action closure. Deduplication uses the accepted proposal/run/attempt and exact provider-ID bytes. A later accepted reply may reuse a raw provider ID; retrying the same accepted proposal cannot regain eligibility by changing its invocation/event UUID. Result-save repair accepts no action closure. Known results remain available if their save fails. Direct-command Continue reports the earlier known result or unresolved attempt instead of dispatching the shortcut again.

Immutable start/finish events retain their exact timestamps across lost acknowledgments. Storage faults are not reclassified as native action failures. Unknown or focus-only effects remain uncertain/unverified; a delivered response is not proof of goal completion. Invalid output-link metadata stops the run and is omitted, while its factual text result remains available. The original legacy JSON bytes remain unchanged, preferences use a separate versioned file, and corrupt/newer database files are preserved. Recovered history creates no grants, review waiters, executable calls or restored native authority.

The journal uses WAL, synchronous FULL/fullfsync, private files, strict schema/identity validation and generation fences. These do not claim protection against arbitrary external writers, physical power loss or every storage/VFS failure. Database and WAL bounds are 128 MiB and 16 MiB. The reusable core `JournalProjection` limits its projection to 100,000 records; the app bridge currently materializes all paged records from the bounded database and does not use that projector. Paged app/UI history remains open.

Output references are local display metadata. Explicit Show in Finder remains available after edits or removed inference grants; automatic content access still needs its separate current scope and canonical identity checks. A crash after a result/artifact checkpoint can restore the output reference before an assistant message was saved. No raw image, audio, native tree, provider envelope or request-header object is admitted to the journal payload. Ordinary visible prose remains exact without a broad secret/PII classifier.
